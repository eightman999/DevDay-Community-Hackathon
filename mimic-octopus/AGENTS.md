# このリポジトリで開発するエージェントへ

## 最初に確認するもの

`README.md`、`docs/GAME-DESIGN.md`、`docs/ART-DIRECTION.md`、`docs/CODEX-HANDOFF.md`、`docs/IMPLEMENTATION-CONTRACT.md`を読み、既存のゲームを起動してから変更方針を決めてください。READMEの未確認欄は、実際の確認結果で更新します。

## 守る体験

- かわいい3Dのミミックオクトパスが、激変するデータの群れに紛れるゲームです。
- 色4種類・形3種類・2タップで覚えて自動継続するリズムの3要素が核です。
- 90秒のソロを成立させ、観察、反応猶予、スキャン、疑われ度、勝敗、再挑戦をつなぎます。
- クリームとココアの縞、表情、8本の柔らかい腕、連続的に変わる輪郭を維持します。カメレオンへの置き換え、単純な丸だけの代用、コンセプト画像を背景にした静止画への退行は避けます。
- 見た目を磨くときも、画面に映る色・形・拍・スキャンと、実際の判定状態を一致させてください。

## 構成

- 静的ファイルは `dist/`。ビルド不要のES Modules構成を基準にします。
- Three.jsは `dist/vendor/three.module.js` を利用します。追加依存は必要性、サイズ、同梱方法、ライセンスを確認します。
- `engine.mjs` はゲームルールを担当し、DOMやThree.jsに依存させません。
- `scene.js` は渡されたスナップショットを描画し、ゲーム状態を変更しません。
- `app.js` は入力、画面遷移、音、エンジンと描画の接続を担当します。
- API契約を維持する変更を優先します。契約を変更する場合は、呼び出し元、テスト、関連ドキュメントを整合させてください。
- 既存コードと素材を基準に改善します。環境やフレームワークの全面変更を最初の作業にしないでください。

## ゲームルールで壊さないこと

- 無操作のまま勝てず、正しく合わせれば勝てること。
- 2タップで覚えたリズムは、操作を続けなくても再現されること。
- スキャン中の不一致が疑われ度に反映され、一致状態には回復の機会があること。
- 一時停止でゲーム、環境、拍、スキャンの時計が止まること。
- フレームが長くなっても、途中の環境更新や勝敗を飛ばさないこと。
- スナップショットを描画側で変更しても、エンジン内部へ影響しないこと。

## モバイルと読みやすさ

- タッチのみで開始から結果・再挑戦まで完結させます。縦画面・横画面の両方を確認してください。
- 操作部は目安として44 CSS px以上を確保し、画面端の安全領域やブラウザUIによる高さ変化を考慮します。
- 色名、形、発光や拍の表示を併用し、色や音だけに重要な情報を任せません。
- 音は任意で、ユーザー操作後に有効化します。一時停止・終了時に音が残らないようにします。
- 動きを減らす設定でも、拍や更新のタイミングを読み取れる代替表示を残します。

## 検証と報告

必要なロジック変更には、実際の失敗や境界条件を確かめるテストを追加・更新します。軽微な装飾変更のために実装をなぞるだけのテストは増やしません。

```sh
npm test
npm run check
```

変更に関係する画面を実際に確認します。基準の例は縦390×844、横844×390です。擬態途中、環境更新、スキャン、一時停止、成功または失敗の各状態で、操作と視認性を確認してください。

テスト通過だけを理由に「実機で確認済み」「画像と同等の品質」と報告しないでください。確認した環境、結果、残る制約を簡潔に記録します。公開や外部共有は、そのセッションにおけるユーザーの許可範囲に従います。
