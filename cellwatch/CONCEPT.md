# CELLWATCH — コンセプト

更新日: 2026-10-18。画面・操作・数値が変わっても参照できる、企画の正本です。[現行試作の仕様](spec.md)と[病院シナリオ候補](SCENARIO-HOSPITAL.md)は別途記録します。

## 一言で

**面白くて遊んでいたら、セキュリティインシデントのことも分かるゲーム。**

ゲームとして面白いことを先に置きます。脆弱性の名前や仕組みを知らなくても遊べて、最後に「実際にもこういう問題がある」と少し学びにつながるくらいを目指します。

まず遊びたくなることを目指します。危険を見つけ、迷いながら対処し、その結果を見てもう一度試す。その過程で、情報を守る判断とインシデントへの対処に触れられる体験をつくります。

## 向き合う社会課題

出発点は個人情報漏洩です。情報の扱いを誤ることが、本人や組織の被害につながる。一方で、専門知識のない人が、インシデントの原因や対処を身近に感じられる入口はつくれるはずだ、という問題意識があります。

背景資料として[個人情報保護委員会の令和7年度年次報告](https://www.ppc.go.jp/aboutus/report/annual_report_2025/)に、漏えい等への対応と普及啓発の取り組みが掲載されています。「多くの人が何も知らない」という割合や、このゲームの必要性・効果を直接証明する資料としては扱いません。

病院の候補では、情報が外へ漏れる問題に加え、必要な情報やシステムを使えず、仕事や診療が止まる問題を扱います。「漏らさない」と「必要なときに使える」の両方が、守りたいものです。

## 誰に遊んでほしいか

専門知識を前提とせず、ゲームとして興味を持った人に遊んでもらうことを想定します。学び始めの学生や、仕事で情報を扱う人も対象候補です。具体的な年齢層や利用場面、研修への採用は未検証です。

## 遊びの核

1. **異変を見つける。** 状況が変わり、放置すると問題が広がることが分かる。
2. **必要な情報を確かめる。** 通してよいものと、止めるべきものを判断する。
3. **対処を選ぶ。** 一件を止める、区画を隔離する、原因に対処する。それぞれに効果と代償がある。
4. **結果を受け取る。** 見落としの被害だけでなく、必要な利用まで止めた影響も返ってくる。
5. **もう一度試したくなる。** 結果を見て、次は違う選択を試す。最後に現実の事例や短い解説へ触れられる余地をつくる。

面白さの仮説は、広がる危険への緊張、限られた時間で選ぶ迷い、対処が効く手応え、再挑戦での上達です。時間制限の長さ、盤面や帳票の見た目、ボタンの配置、点数の名前は、この体験を成立させるために調整します。

## 遊んだあとに残したい気づき

[脆弱性11種の解説候補](LEARNING-TOPICS.md)は、この振り返りで触れられる題材です。ゲームの敵を11種にしたり、すべての攻撃を再現したりする要件ではありません。専門用語の暗記や解説の読了を、楽しむための条件にはしません。

| 遊びで経験すること | 伝えたい判断 |
| --- | --- |
| 条件を確認して通す／止める | 見た目や雰囲気だけで決めず、相手・権限・送り先などを確かめる |
| 問題を放置すると影響が続く | 最初の見落としの後も対処が必要になる |
| 正常な利用まで止めると困る人がいる | セキュリティと業務の継続を両方考える |
| 隔離と原因への対処を使い分ける | 一時的な封じ込めと再発防止の役割が違う |
| 原因に対処しても既存の被害は残る | 再発防止と、情報・業務を元に戻す復旧を分けて考える |

これは目指す学びです。現実のすべての事故対応を代表するルールではなく、理解度や事故削減への効果は測定が必要です。

## 方向性と未決事項

| 状態 | 内容 |
| --- | --- |
| 企画の軸 | 面白いゲームを入口に、セキュリティインシデントの判断と対処に触れる |
| 企画の軸 | 危険を止めることと、必要な利用を守ることの葛藤をつくる |
| 第一候補・未確定 | WannaCry/NHSの事件を参考にした架空の病院ステージ |
| 現行試作の選択 | 夜間監視、120秒、16申請、4領域、紙の申請書、セル盤面、保全率と信頼、隔離8秒・修復10秒 |
| 採用方針 | 音楽制作に加え、レビューにもDotsを使う |
| 振り返りの題材候補 | SMBv1/WannaCry、認証回避、SQLインジェクションなど11種。掲載と見せ方は未定 |
| 今後調整する | 最終的な舞台、画面、操作、指標、難易度、各対処の時間と代償 |
| 未検証 | 初見の分かりやすさ、面白さ、理解の変化、再挑戦意向 |

現行試作の「修復」は、既存の脅威の除去と新規不正申請の予防をまとめたゲーム上の操作です。失った保全率・信頼は回復しません。病院案では、感染防止、感染済み端末への対処、情報や業務の復旧をどこまで分けるかを設計します。

## 体験を支える技術の方針

ゲーム内BGMはDotsで制作した音楽を採用する予定です。現在制作を進めており、音楽で作品の雰囲気や演出を支えます。DevDay技術をゲームの実行だけでなく、作品の素材づくりにも活用します。

レビューにもDotsを採用します。レビューの指摘や気づきを次の改善へつなげる役割を担わせます。

MCP EventsやAgents APIなどDevDay関連技術の活用を、作品の技術的な柱として重視します。意味のあるゲーム状況の通知、相棒の対応や演出、最後の短いまとめなど、何のために使うかを定め、実装と動作の証拠を揃えます。画面配置や11の学習題材に技術を固定しません。

現在確認できた接続コードは、別ブランチ `main` のDecisions APIによる次の通信候補の選択です。MCP Events／Agents APIの用途と接続は別に確認・設計します。技術ごとの状態と根拠は[FEATURES](FEATURES.md)を正本とします。

## 次の設計で確かめること

- 用語を覚える前から、何を守りたいのかが伝わるか。
- 正しい選択を当てるだけでなく、対処の順序や代償に面白さがあるか。
- 「全部止めれば安全」と受け取らず、必要な利用を守る意味を理解できるか。
- 失敗の理由を知った後、もう一度遊びたくなるか。
